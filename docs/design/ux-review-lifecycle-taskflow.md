## 问题清单

### 问题1：Agent 生命周期管理交互不合理

**现状描述：**
- 当前只有一个 Table + 统计卡片，用户不理解如何管理
- 每行有2个重复复选框
- 缺少 agent 详情查看、任务干预、配置修改等管理方式

**根因分析：**
1. **信息密度过载**：Table 试图展示所有信息，但缺乏层次结构，用户无法快速定位关键信息
2. **交互意图不明确**：用户看到 Table 却不知道能做什么操作，没有明确的"可行动"线索
3. **复选框设计缺陷**：同一行出现2个复选框，用户困惑于它们的区别和用途
4. **缺少状态感知**：无法一眼看出 agent 的健康状态、当前任务、资源占用情况

**设计方案：**

#### 布局重构（参考 Linear 的简洁列表 + 详情面板模式）

```
┌─────────────────────────────────────────────────────────────┐
│  [过滤器] [搜索]                    [+ 新建Agent] [批量操作▼] │
├─────────────────────────────────────────────────────────────┤
│  ┌──────────────┬─────────────────────────────────────────┐ │
│  │              │                                         │ │
│  │  Agent 列表  │           Agent 详情面板               │ │
│  │  (可折叠)    │           (默认收起/点击展开)           │ │
│  │              │                                         │ │
│  │  🔴 agent-01 │  ┌─────────────────────────────────┐   │ │
│  │  🟢 agent-02 │  │  基本信息 | 任务 | 配置 | 日志   │   │ │
│  │  🟡 agent-03 │  ├─────────────────────────────────┤   │ │
│  │              │  │  状态: 🟢 运行中                 │   │ │
│  │              │  │  当前任务: task-xxx (分析中)     │   │ │
│  │              │  │  CPU: 45% | 内存: 1.2GB          │   │ │
│  │              │  │                                 │   │ │
│  │              │  │  [停止] [重启] [查看日志] [编辑] │   │ │
│  │              │  └─────────────────────────────────┘   │ │
│  │              │                                         │ │
│  └──────────────┴─────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

#### 列表项设计

每行 Agent 卡片包含：
- **左侧**：单选框（仅一个）+ 状态指示器（彩色圆点）
- **主体**：Agent 名称 + 角色标签 + 当前任务缩略
- **右侧**：快捷操作按钮（悬停显示）：查看、停止、重启
- **底部**：资源使用条（CPU/内存微型进度条）

#### 状态指示器规范

| 状态 | 图标 | 颜色 | 说明 |
|------|------|------|------|
| 健康运行 | ● | 绿色 #22c55e | 正常执行任务 |
| 空闲待命 | ● | 蓝色 #3b82f6 | 无任务，等待分派 |
| 异常告警 | ● | 黄色 #eab308 | 有非致命错误 |
| 已停止 | ● | 灰色 #6b7280 | 手动停止或崩溃 |
| 离线失联 | ● | 红色 #ef4444 | 超过30秒无心跳 |

#### 批量操作栏

选中多个 Agent 后，顶部浮现批量操作栏：
- [批量停止] [批量重启] [批量同步] [批量清理]
- 显示选中数量："已选择 5 个 Agent"

**优先级：P0**

**参考：**
- Linear：简洁的列表+详情面板模式，键盘友好
- Notion：数据库视图切换（Table/列表/看板）
- Docker Desktop：容器状态可视化

**风险点：**
1. 详情面板实时数据刷新可能增加服务端负载 → 建议 WebSocket 推送或 5s 轮询
2. 移动端面板展开可能遮挡列表 → 采用抽屉式从右侧滑出

### 问题2：无法强行管控 agent 间任务流转

**现状描述：**
- 没有界面让用户主动干预任务（审批/驳回/分派/停止/恢复/取消）
- 用户无法看到任务当前在哪个 agent 上，状态是什么

**根因分析：**
1. **缺乏任务视角**：当前设计以 Agent 为中心，而非以任务为中心，用户无法追踪任务生命周期
2. **操作入口隐藏**：任务干预操作需要知道 API 端点，没有直观的 UI 入口
3. **状态不透明**：任务状态变化没有可视化，用户不知道任务流转到了哪个环节
4. **缺少审批流程**：任务从创建到执行缺乏人工审核节点，高风险操作无法拦截

**设计方案：**

#### 任务看板视图（参考 Jira 看板 + Linear 的简洁）

```
│  [看板视图 ▼] [列表视图] [时间线]      [+ 新建任务] [🔔 待审批 3]    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
```

#### 任务卡片设计

每个任务卡片包含：
- **标题**：任务名称（可点击展开详情）
- **类型标签**：颜色区分任务类型（分析/生成/运维/交易）
- **优先级**：🔴 高 / 🟡 中 / 🟢 低
- **指派信息**：当前 Agent 或 "未分派"
- **进度条**：如果是长时间任务，显示进度百分比
- **快捷操作**：根据状态显示不同操作按钮

#### 状态流转操作

| 当前状态 | 可操作 | 按钮样式 |
|----------|--------|----------|
| planned | 审批通过 / 驳回 | [通过] 绿色 [驳回] 红色 |
| approved | 分派给 Agent | [分派 ▼] 下拉选择 |
| dispatched | 开始执行 | 自动流转，无需操作 |
| in_progress | 停止 / 查看进度 | [停止] 黄色 [进度] |
| stopped | 恢复 / 取消 | [恢复] 绿色 [取消] 灰色 |
| completed | 查看结果 / 归档 | [查看结果] |
| rejected | 重新提交 / 删除 | [重新提交] [删除] |

#### 任务详情抽屉

点击任务卡片打开右侧抽屉：
- **基本信息**：创建时间、创建人、优先级、标签
- **状态时间线**：显示状态变更历史（谁、何时、从什么到什么）
- **当前执行**：Agent 信息、实时日志（WebSocket 流式）
- **思考链路**：Agent 的推理过程展示
- **操作区**：根据状态显示可用操作

**优先级：P0**

**参考：**
- Jira：成熟的看板拖拽和状态流转
- Linear：简洁的列表视图和快捷操作
- GitHub Actions：实时日志流式展示

**风险点：**
1. 看板拖拽操作可能误触 → 增加确认弹窗，或仅支持按钮操作
2. 实时日志流式传输数据量大 → 限制显示最近 100 条，提供"查看完整日志"链接
3. 多人同时操作同一任务 → 后端加乐观锁，前端显示"已被他人操作"提示

### 问题3：Agent 管理方式太少

**现状描述：**
- 当前只有"同步"和"清理"两个操作
- 缺少：查看详情、任务干预、修改配置、健康监控

**根因分析：**
1. **功能覆盖不全**：只实现了最基础的生命周期操作，缺少运维和诊断能力
2. **配置管理缺失**：Agent 的配置分散在各处，没有统一的配置界面
3. **可观测性不足**：没有健康指标、性能监控、告警机制
4. **故障排查困难**：出问题后无法快速定位原因，缺少日志和诊断工具

**设计方案：**

| 修改配置 | Agent 详情 → 配置 Tab | 编辑模型、温度、最大token等 |
| 健康监控 | Agent 详情 → 监控 Tab | 查看性能图表、设置告警 |

**参考：**
- Docker Desktop：容器运维完整工具链

- Kubernetes Dashboard：配置管理和资源监控

**风险点：**
1. 配置修改可能导致Agent行为异常 → 增加配置预览和"重置默认"按钮
2. 实时监控图表数据量大 → 默认显示最近5分钟，支持时间范围选择
3. 日志查看可能暴露敏感信息 → 增加日志脱敏开关

### 问题4：任务流图形展示差

**现状描述：**
- 任务只在一个 Table 里，看不到流转路径
- 没有状态流转图、时间线、进度可视化

**根因分析：**
1. **数据孤岛**：任务状态信息以列表形式呈现，缺乏关联和时序关系
2. **心智负担重**：用户需要在大脑中构建任务流转路径，增加了认知负荷
3. **异常难发现**：表格很难发现任务卡在某状态、长时间未流转等异常情况
4. **缺乏进度感知**：长时间运行的任务没有进度条，用户不知道还要等多久

**设计方案：**

#### 3. 任务进度可视化

对于长时间运行的任务（如数据处理、代码生成），显示：
- **进度条**：百分比 + 预估剩余时间
- **阶段指示**：当前执行到哪个阶段（如 "下载数据 → 清洗数据 → 分析 → 生成报告"）
- **实时日志**：最近3条日志滚动更新
- **思考链路**：Agent 的关键决策节点

当有多个任务同时运行时，用泳道图展示并行状态：
- 横轴：时间线
- 纵轴：不同的 Agent 泳道


**优先级：P1**

**参考：**
- Mermaid.js：状态图语法
- GitHub Actions：任务时间线和进度展示
- VS Code Remote：SSH连接进度可视化

**风险点：**
1. 图形渲染在数据量大时可能卡顿 → 限制同屏显示任务数，超过则分页或折叠
2. 实时进度推送增加WebSocket负载 → 进度更新频率限制为每秒1次
3. 移动端图形展示空间有限 → 移动端只显示简化的状态列表

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| WebSocket连接不稳定 | 实时数据丢失 | 断线重连 + 本地缓存 + 状态同步 |
| 多人同时操作冲突 | 数据不一致 | 后端乐观锁 + 前端冲突提示 |
| 数据量大渲染卡顿 | 用户体验差 | 虚拟列表 + 分页加载 + 懒加载 |
| 移动端功能受限 | 核心操作无法完成 | 移动端仅支持查看和通知，操作引导到PC |
