### 问题 1：20 步流水线映射不完整（❌ 严重）

**位置**：PRD 第 6 节"工作流模板示例" → 6.1 研发流水线工作流

**问题描述**：
PRD 中的工作流模板示例未能准确映射 `rd-team-workflow.md` 定义的 20 步主线流程：

| 基线文档 | PRD 模板 | 问题 |
|---------|---------|------|
| Step 5：UI + 架构 + 数据库设计（三个独立互审组） | step5_design：parallel 内三个子步骤 | ❌ 未体现三组互审（ui-designer ↔ ui-checker / rd-dba ↔ dba-checker），仅显示并行执行 |
| Step 11：多轮 Code Review（2-4轮） | step11_code_review：min_rounds: 2, max_rounds: 4 | ✅ 正确 |
| Step 12：首次走查（双产品 + 双 UI） | step12_walkthrough | ⚠️ 未明确"双产品走查 + 双 UI 走查"的互审要求，仅写 parallel agents |
| Step 13：前后端联调验证 | step13_integration | ✅ 正确（新增独立步骤） |
| Step 14：送测 + 自动提交 GitHub | step14_submit_test | ✅ 正确 |
| Step 15：测试编写 | step15_test_write | ✅ 正确 |
| Step 16：测试验证 | step16_test_validation | ✅ 正确 |
| Step 17：测试循环（3-6轮） | step17_test_loop | ✅ 正确 |

**影响**：
- 用户使用模板启动工作流时，无法执行符合 `rd-team-workflow.md` 规范的流程
- Step 12 首次走查的互审要求缺失，可能导致走查质量不符合团队规范

**建议修改**：
1. 在 `step5_design` 的 YAML 中明确添加 `checker` 字段和互审要求：
```yaml
- id: step5_design
  name: UI + 架构 + 数据库设计
  parallel:
    - id: ui_design
      agent: ui-designer
      checker: ui-checker  # 互审方
      review_required: true
      min_issues: 3  # 互审方必须提出 ≥3 个问题
    - id: arch_design
      agent: rd-backend-arch
    - id: db_design
      agent: rd-dba
      checker: dba-checker  # 互审方
      review_required: true
      min_issues: 3
```

2. 在 `step12_walkthrough` 中明确双走查要求：
```yaml
- id: step12_walkthrough
  name: 首次走查
  parallel:
    - id: product_walkthrough
      agents: [rd-product-manager, rd-pm-checker]  # 双产品
      validation:
        - 产品验收逐条核对 PRD
    - id: ui_walkthrough
      agents: [ui-designer, ui-checker]  # 双 UI
      validation:
        - UI 走查通过
```

### 问题 2：关键控制功能优先级错配（❌ 严重）

**位置**：PRD 第 9 节"优先级排序" → P0/P1 划分

**问题描述**：
以下功能在需求文档中被定义为**核心能力**，但在 PRD 中被推迟到 P1/P2，与 MVP 核心价值冲突：

| 功能 | 需求文档定义 | PRD 优先级 | 冲突原因 |
|------|------------|-----------|---------|
| F24 强制完成单步 | 2.4 控制能力（核心） | P1-09 | MVP 若不支持，步骤卡住时用户无法干预 |
| F25 重新分配 Agent | 2.4 控制能力（核心） | P1-10 | MVP 若不支持，Agent 故障时无法恢复 |
| F28 超时预警 | 2.5 进度与时间估算 | P1-28 | MVP 若不支持，用户无法感知超时风险 |

**需求文档原话**（4.3 Agent 不可用）：
> "长时间无 Agent → 超过 30 分钟无可用 Agent → 发送告警通知"
> "恢复机制：Agent 恢复后自动接收等待中的任务，支持手动重新分配到其他 Agent"

这表明"重新分配 Agent"是处理 Agent 故障的**必要能力**，不应推迟到 P1。

**影响**：
- MVP 用户遇到步骤卡住、Agent 故障、超时风险时，缺乏必要的干预手段
- 违反需求文档定义的"精准控制"核心价值（控制粒度：步骤级）

**建议修改**：
1. 将 F25 重新分配 Agent 提升到 **P0**：
```
P0-19 | 控制能力 | 重新分配 Agent | ⭐⭐⭐⭐⭐ | 3 | P0-08
```

2. 将 F24 强制完成单步提升到 **P0** 或 **P1-01**（MVP 后第一批）：
```
P1-01 | 控制能力 | 强制完成单步 | ⭐⭐⭐⭐ | 2 | P0-15
```

3. 将 F28 超时预警提升到 **P0** 或 **P1-02**：
```
P0-20 | 进度感知 | 超时预警 | ⭐⭐⭐⭐ | 2 | P0-13
```

调整后 P0 工作量：87 + 3 + 2 + 2 = **94 人天**（增加 7 人天，仍在合理范围）

### 问题 3：数据模型字段扩展未纳入 P0（⚠️ 中等）

**位置**：PRD 第 7 节"数据模型概要" → 7.2 核心实体定义

**问题描述**：
PRD 第 10 节"与现有页面的集成点"提到：
- 10.2.1："任务表新增字段：`workflow_instance_id`, `step_execution_id`"
- 10.3.1："会话表新增字段：`workflow_instance_id`, `step_execution_id`"

但在 P0-16"核心表设计与迁移"中，**未明确包含**这两个现有表的字段扩展。

**影响**：
- 若 P0 MVP 不包含 Tasks/Sessions 的字段扩展，工作流步骤无法与现有任务/会话关联

**建议修改**：
在 P0-16 的描述中明确包含：
```
P0-16 | 数据模型 | 核心表设计与迁移 | ⭐⭐⭐⭐⭐ | 5 | 无
  - 新增表：workflow_templates, workflow_instances, step_executions, review_records
  - 扩展现有表：tasks（新增 workflow_instance_id, step_execution_id）
  - 扩展现有表：sessions（新增 workflow_instance_id, step_execution_id）
```

### 问题 7：WebSocket 断线重连机制规格不完整（⚠️ 轻微）

**位置**：PRD 第 5 节"DAG 可视化规范" → 5.5 性能优化

**问题描述**：
PRD 提到 WebSocket 推送的节流策略（100ms），但**未详细说明断线重连机制**：
- 重连间隔策略（需求文档 4.6 提到指数退避：1s, 2s, 4s, 8s, 16s, 30s）
- 重连失败后的降级策略（需求文档提到 HTTP 轮询 5 秒一次）
- 离线模式下的用户提示

**建议修改**：
在 PRD 5.5 或 8.7 WebSocket 事件章节中补充断线重连规格：
```markdown
### WebSocket 断线重连机制

- **重连策略**：指数退避（1s, 2s, 4s, 8s, 16s, 30s，最大 30s）
- **最大重连次数**：10 次
- **重连失败降级**：切换到 HTTP 轮询（5 秒一次）
- **用户提示**：显示"离线模式（数据可能不是最新）" + 手动刷新按钮
- **恢复切换**：WebSocket 连接成功后自动切换回实时模式
```
